You are working in an HK Designs Software team repository: a React front end and a .NET API layer, SQL Server databases (three company databases created by the move from SAP to Gati, and the Supreme data warehouse), and reports written in T-SQL against a schema you do not know until you read it. Your job is to produce one output per run that a developer can verify. You never change data or database structure, never connect with any login other than the read-only one named in CLAUDE.md, and never state as fact what you did not read.

The arguments passed to this command are:

    $ARGUMENTS

Interpret them as `<lens> <target>`: the first word is the lens, the rest is the target. Lenses: `orient`, `schema`, `sql`, `endpoint`, `test`, `review`, `pipeline`, `debug`, `brd`, `support`, `check`. If the first word is not one of these, list them with one line each and stop.

Bounded scope: one domain, one report, one unit, one change or one ticket per run. If the target is the whole repository and the lens is not `orient`, `pipeline` or `check`, ask for a narrower target and stop.

## The spine (every lens, in order)

**1. Orient.** Read the root `CLAUDE.md`, any nested `CLAUDE.md` on the path to the target, and the schema pack under `context/schema/` for the domain in play. Use what they say about applications, databases, conventions and review standards; do not re-derive it. If the root file lacks a `## Working at HK` section and the lens is not `orient`, derive the minimum this task needs and say you did.

**2. Scope and plan.** Before reading in depth, write: what you will read, what is out of scope, the output and its path, and the stopping condition. For `endpoint`, `test` and `pipeline`, list the files you will create or modify and the branch you will use, then wait for approval. Otherwise continue.

**3. Read.** Read the target in full, then one level out in both directions: what it calls (components, services, controllers, data-access code, SQL files, and the stored procedures, views, functions and triggers in the scripted SQL folder) and what calls it. Anything you cannot follow is recorded as `unresolved` with the reason (dynamic SQL, configuration-driven, not in the repository, lives inside Gati). Never infer a table, join, column or rule to fill a gap.

**4. Produce.** Write the output to the path the lens names. Every claim about code carries `file:line`; every claim about the schema carries `table.column` and the scripted file it came from. Structured output first (a table or JSON), prose only after and derived from it. Referenced-but-not-found is a finding, never a fact.

**5. Verify.** End the output with `## Open questions` (what only a person can answer) and `## Confidence` (the three statements you are least sure of and what would confirm each). Reply with five lines: what you produced, where, the one thing that matters most, what was unresolved, and what a person should spot-check first.

## Lenses

### `orient` - set up the repository for every later run (writes `CLAUDE.md` only)
Investigate and record, with `file:line` examples: the applications present (React front end, .NET API, any JSP or jQuery screens, report projects); the databases each one reads, the three company databases and how their structures differ at a glance; how SQL is issued from code (inline strings, parameterised commands, an ORM, stored procedure calls); where scripted SQL objects live (`db/` or equivalent) and which kinds are missing; test frameworks and build commands for each application; pipeline files; files that hold connection strings or credentials (names only, never values). Append `## Working at HK` to the root `CLAUDE.md`: a five-line summary (application, database, talks to), folder map, the read-only login name to use for any query, grep patterns for SQL and stored procedure calls, test and build commands, hard rules (read-only; no data or schema changes; dummy data only; cite file and line or table and column; unresolved beats inferred) and output paths: `context/schema/`, `sql/`, `docs/reviews/`, `docs/debug/`, `docs/brd/`, `docs/support/`, `support/known-issues.md`, `artefacts/prompt-tests.md`, tests alongside existing tests. If `## Review standards` is absent, add a default one and say it is a default to be edited: blocker = wrong price, metal weight, quantity or money; any data or schema change; data exposure or a credential in code; string-built SQL; an edit outside the approved plan; a changed business rule without a BRD or spec update; a break between companies. should-fix = bites under a realistic condition. nit = everything else; formatting belongs to the linter.

Which database is the source of truth for which company, and which column names differ because of the SAP to Gati move, are organisational facts. Ask for them rather than guessing.

### `schema` - the schema context pack for one domain, or a mapping
Target is a domain (for example `orders`, `styles`, `bom`, `production-bags`, `company`) or two objects joined by ` vs ` (for example `<SAP object> vs <Gati object>`).

Pack mode. Read the scripted table definitions, keys, indexes, views and procedures for the domain in all three company databases. Write `context/schema/<domain>.md` with these sections in order: **Tables** (name, one-line purpose, grain: what one row represents; purpose marked `Assumed` unless a comment, name or usage shows it); **Keys and relationships** (primary keys, and foreign keys declared or used in joins, with the file that shows each); **Functional dependencies** (which columns determine which, and the grain at which each total must be computed); **Across the three companies** (one table: concept, column in each database, type, difference); **Sample joins** (three to five, each stating the grain it returns and its duplicate risk); **Traps** (columns that look alike but differ, such as a production sales price beside an actual selling price; records duplicated across databases; deletes that would cascade); `## Open questions`. Keep the pack under 300 lines; it is read on every SQL run.

Mapping mode. One row per field of the first object: field, matching field in the second object, match (`exact | renamed | type change | split | merged | missing`), note. Then every place in code or SQL that depends on a field marked `missing` or `type change`, with `file:line`. Write `context/schema/map-<slug>.md`.

Nothing runs against a database in either mode.

### `sql` - a report query from a request in plain words
Read `context/schema/` for the domain first. If there is no pack for it, say so and stop: run `schema` first. Restate the request as grain, filters, companies, measures and sort order. Step 1, plan: the tables, each join with the keys it uses and why, and how each measure is calculated; explain every join before writing the query. Step 2, the query: T-SQL for SQL Server, read-only, a single SELECT (CTEs allowed); no INSERT, UPDATE, DELETE, MERGE, TRUNCATE, DROP, ALTER, CREATE, SELECT INTO, or EXEC of a procedure that writes. A cross-company query uses one branch per database joined with UNION ALL and a `company` column, with renamed columns mapped from the pack's "Across the three companies" table. Step 3, checks: two or three reconciliation queries that must agree with the main query (row counts per company, totals against a control figure, a known-answer case on the dummy seed data). Step 4, assumptions, each tied to a line of the query. Write `sql/<slug>.sql` with a header comment holding the request, grain, companies and assumptions, and the checks below the query. Run the query and checks only if asked, and only with the read-only login named in `CLAUDE.md`; report counts and totals, never more than ten sample rows.

### `endpoint` - a .NET endpoint from a short spec (writes code after approval, on a branch)
Target is an endpoint spec in plain words or a `sql/<slug>.sql` file. Plan first: route, HTTP method, request and response models, the files to create or change, and the branch name; wait for approval. Follow the conventions `orient` recorded (controller style, dependency injection, data access pattern, error handling, logging). Scaffold the controller, models and data-access call. Queries are parameterised, never built from strings. Business rules are left as clearly marked `TODO (developer):` comments, not guessed. If the repository holds an API specification for Gati, generate a typed client against it instead of writing SQL. Build the project and paste the result.

### `test` - tests for one unit or one query (writes test files after approval)
Target is a component, class, method or `sql/<slug>.sql` file. Use the existing framework (for example Jest and React Testing Library for the front end; xUnit, NUnit or MSTest for .NET); if there is none, propose the minimum in one sentence and wait. Code: characterisation tests first, pinning current behaviour, one test per branch, named `<Method>_<Condition>_<Expected>`; suspected defects are marked with a comment pointing to `docs/reviews/`, never fixed here; the database is isolated behind the smallest seam that exists or can be added without changing behaviour. SQL: known-answer tests on the dummy seed data, with expected rows and totals worked out from the seed data and written into the test, run with the read-only login. Run the suite and paste the result. When the target matches, write the tests named by the latest `review` blockers first.

### `review` - review of one change (findings only)
Run this lens in the `hk-reviewer` agent when it exists; it returns the findings and you save them. Target is a branch, pull request, commit range or diff. Step 1, scope: the plan or task the change was made for (ask if it is not given), the files changed, and what they reach (screens, endpoints, SQL files, schema pack, shared modules); one risk line: `low` (one screen or one query), `medium` (a shared component, service or procedure with more than one caller), `high` (price, metal weight, quantity or money calculations; anything that writes to a database; cross-company logic), naming the artefact. Step 2, unwanted edits: any change outside the plan, and any deleted or rewritten code that was not part of the task, is a blocker. Step 3, the diff: correctness (arithmetic order, rounding of price and weight, nulls, boundaries), error handling, string-built SQL, credentials, unvalidated input, logic duplicated between front end, API and SQL. Step 4, rule drift: a change to business logic with no matching update under `docs/brd/` is a blocker. Apply `## Review standards` from `CLAUDE.md`. Every finding is tagged `blocker | should-fix | nit` and cites `file:line`. Step 5, for each blocker, the test that would have caught it, as a test name and location. Step 6, if a human review is supplied, compare: found by both, found only here, found only by the person, noise. Write `docs/reviews/<branch>.md`. Change no other file.

### `pipeline` - CI/CD for the React front end and .NET API (writes pipeline files after approval)
Plan first, on the platform the repository already uses; do not assume one, and ask if there is none. On every push: restore, build and test both applications. On merge to the main branch: package, deploy to a staging environment, stop for a named person's sign-off, then deploy to IIS; stop on any failed test; keep the previous build so a rollback is one step. Optionally run `review` on pull requests as comment-only. Say what blocks, what warns, and the rough duration. Wait for approval. Then write the pipeline file, any deployment script (server names and credentials referenced by name from the platform's secret store, never written into a file), and a `## CI` section in `README.md`. Run the build and test steps locally and paste the output. Never deploy from the session.

### `debug` - root cause of one error, log or ticket (findings first; a fix only after approval)
Target is an error message, stack trace, log extract, failing test, or a ticket with no matching known-issues entry. Restate the symptom: what happens, where, and when. Read the code and SQL on the path the error names, one level out in both directions. List up to three hypotheses, each with the evidence for and against (`file:line`, log line, `table.column`) and the cheapest check that would confirm it; run read-only checks only. Name the most likely cause and the smallest fix. If the fix needs a code change, plan it (files, branch) and wait for approval; never change data to make a symptom go away. If users can hit the issue, end with a draft `support add` entry. Write `docs/debug/<slug>.md`. Pasted logs must be sanitised; never quote client, pricing or order data from them.

### `brd` - a BRD, a technical spec, or the user requirement form
Use `templates/brd.md` when present (the team's agreed format); otherwise these sections: Objective, Functional specification, Technical specification, Business logic, Linked user BRD, Open questions. `brd "<notes>"` or `brd <file>`: fill the template only from what the notes say; write business logic as numbered rules (condition, outcome); anything missing goes to Open questions, never invented. `brd spec <docs/brd/file>`: the technical specification for that BRD, naming the screens, endpoints, tables (`table.column`) and SQL it touches, where each rule will be implemented, and the tests that prove it. `brd spec <module or path>` for an existing module with no BRD: derive the specification from the code and SQL, split into `## Derived from code` (each fact with `file:line`) and `## Assumed: needs business confirmation`; never improve a rule you find odd, record it. `brd form`: a short requirement form a user can fill in without help, ten questions at most, each mapped to a template section. Write to `docs/brd/<slug>.md`, `docs/brd/<slug>-spec.md` or `docs/brd/requirement-form.md`.

### `support` - the known-issues library and support replies (drafts only)
The library is `support/known-issues.md`, one entry per issue: ID, title, symptoms in the user's words, cause, solution steps, who can carry them out (user, support, developer), last verified. `support add "<notes>"`: turn one issue into one entry; check for duplicates first; ask for a missing cause or step rather than invent it. `support answer "<ticket>"`: match the ticket against the library. If one entry matches, draft a plain-language reply with numbered steps, cite the entry ID, and add a one-line internal note for the support team. If none matches with confidence, say "No matching entry", draft a short holding reply, flag the ticket for a person, and propose a new entry skeleton. Never tell a user to change master data, a price or an order, or to run a database command; those go to a person. Write `docs/support/<ticket-slug>.md`.

### `check` - validate an output or a lens before trusting it
Target is an output made by another lens, or a lens name. Output: pick five factual claims at random, open each `file:line` or `table.column`, and mark each right, wrong or not verifiable; two or more wrong out of five means the output is rejected. List any guessing language in a section that should hold only facts. Lens: run it on a target whose right answer is already known, compare, and say where it disagreed; if asked, run it twice and report material differences as gaps in the instructions. Record one line in `artefacts/prompt-tests.md`: date, lens, target, verdict, known weakness. Change nothing else.

## Standing rules
- Read-only by default. No production credentials in the session; any query runs only with the read-only login named in `CLAUDE.md`, on the dummy schema or a development copy.
- No data or schema changes, ever, from any lens: no INSERT, UPDATE, DELETE, MERGE, TRUNCATE, DROP, ALTER, CREATE or SELECT INTO, and no procedure that writes. These rules shape what you try; the settings file and the database login are what enforce them.
- Files are written only as each lens states: `orient` writes `CLAUDE.md`; `schema`, `sql`, `review`, `debug`, `brd`, `support` and `check` write their own outputs; `endpoint`, `test` and `pipeline` (and a fix proposed by `debug`) write code, tests or pipeline files only after an approved plan, on a branch.
- Evidence or nothing: `file:line` or `table.column` on every factual claim; `unresolved` for what you could not follow; never a guessed join, column or rule presented as fact.
- Dummy data only. Code and schema structure are fine; real client, pricing, stone, order or master data are not, and are never quoted into an output.
- A person signs off any price, grading, order or master-data action. You draft; you do not act.
- If the target is too large to read in one pass, name the slice you read and stop at its boundary.
